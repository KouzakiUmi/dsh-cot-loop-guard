# 为什么在 DSH 的输出提交边界做守卫

[中文首页](../README.md) | [English](LAYERING.en.md) | [算法与完整设计](DESIGN.zh-CN.md)

## 结论先行

选择的不是“只在 UI 拦一下”，也不是“给模型再写一句不要循环”，而是 **DSH Host 内、模型适配器已经产出结构化 chunk 之后、这些内容进入已接纳输出流之前** 的边界。

这里的“提交边界”指进入统一的输出组装、实时发布和后续持久结算路径，不表示每个字符都即时写盘，更不表示 UI、网络和磁盘构成一个原子事务。

参考实现采用三层协作：

- **策略插件**判断何时缓冲、放行、抑制精确副本、申请中断或有限恢复。
- **Core 调用循环**掌握模型调用、取消、迭代器清理、工具结算和持久前缀，负责真正执行决策。
- **Client/桥接层**展示真实状态，处理活动重连与同一步内的多次调用，不代替后端决定哪些内容进入历史。

这是为了在有足够语义信息的地方止损，同时不让纯检测逻辑越权操作会话和工具。它是本参考实现的工程选择，不是声称其他系统只能采取相同架构。

## 1. DSH 的设计使问题横跨多个层

### 1.1 模型请求不是一个单独的文本框

一个调用至少同时涉及：

```text
Agent / turn / step 的任务上下文
    -> prepared call：适配器、模型、重放能力已确定
    -> 异步 chunk 流：reasoning、text、工具片段、usage、finish
    -> 输出策略：哪些内容可以接纳，是否需要停止本次调用
    -> 已接纳流
        -> block 组装
        -> 紧凑 stream 记录（结算时持久化）
        -> 实时帧和 UI 投影
    -> 结算 / 工具派发 / 后续请求
```

相同的一段 reasoning 可能同时出现在实时显示、最终 assistant message、持久 stream，以及下一次请求的重放历史里。只改其中一个副本，不等于减少整个会话里的冗余。

### 1.2 插件化不意味着插件天然拥有调用控制权

在参考代码中，策略通过带类型的 `agent/output-policy` 扩展点参与调用。它不是把一段全局字符串处理器注入每个供应商 SDK，也不是直接修改安装目录中的运行文件。

**该扩展点包含本方案所需的 Core 改动**：不能把它描述成在所有原版 DSH 上都已经存在的通用插件接口。这里发布的是特定参考快照，不是“安装一个插件即可适配任何版本”的承诺。

参见 [Core 请求循环](../reference/packages/core/agent-loop/src/agent.ts#L444-L488) 和 [策略注册](../reference/packages/guard/repeat-tool-reminder/src/reasoning-policy.ts#L218-L258)。

### 1.3 统一事件外观不等于所有内容都能随意编辑

适配器可以把不同供应商协议映射成相似的 chunk，但重放约束未必相同。推理文本可能关联签名、不透明元数据或特定重放字段。

因此必须等到**同一次 prepared call**的能力已经确定，再决定是否挂载编辑策略。不能从模型显示名称猜“这一家应该可编辑”，也不能把底层限制留给 UI 自己判断。

### 1.4 Host 语义不应由某个窗口拥有

DSH 的调用、会话和工具执行语义位于 Host/Agent 一侧，Chat 是这些事实的一种呈现。把判定和取消只绑定到某个桌面窗口、页面组件或当前选中的会话，会把“是否在看这个 UI”错误地变成保护条件。

在实际挂载该策略的组成中，守卫应跟随 Agent 调用生命周期；Web、桌面、原生子代理或其他消费者再决定如何展示。并非每个 Profile 都自动启用了策略，也不是关闭/重新打开一个组件就应重置后端的调用状态。桌面壳的窗口管理仍有自己的职责，但不能替代模型输出和会话结算边界。

## 2. 为什么不能只做在其他层

这些层各有用途，下面比较的是“只做在该层”对本目标的局限，不是否定它们。

| 层面 | 可以解决什么 | 单独使用时为什么不够 |
|---|---|---|
| 提示词、系统指令 | 提醒模型换方法、降低部分重复倾向 | 模型可能在输出中不断重复这条提醒；指令本身不能强制终止当前流或阻止历史继续增长 |
| 工具执行后提醒 | 发现相同工具和参数反复调用 | 模型可能始终没有发出工具调用，只在 reasoning 中反复承诺行动；事后工具钩子还没有介入机会 |
| UI 隐藏或折叠 | 减轻视觉干扰，提供用户操作入口 | 后端仍可能接纳、持久化并重放原文；其他视图、SDK 或原生子代理也未必依赖这个 Chat 组件 |
| 供应商 SDK | 解析协议、识别传输状态、取消请求或限制输出 | 单独并不负责 DSH 的 turn/step、持久前缀、未派发工具和策略恢复预算；把这些都塞进去会重新引入 harness 级职责 |
| 网络代理/流文本替换 | 观察协议字节、执行部分集中规则 | 常缺少 Agent 生命周期与最终组装信息；原始文本替换还可能破坏工具参数、签名和重放一致性，最终仍需应用协作 |
| 持久化之后清洗/压缩 | 整理已经存在的历史，辅助人工交接 | 无法撤销已消耗的生成成本，也不能阻止这段内容先进入历史；改日志还必须处理来源、重放和一致性 |
| 供应商输出上限/普通重试 | 限制单次生成或处理部分请求失败 | 上限可能太晚，重试可能重复相同输入；不等于检测“有输出但没有进展”，无条件重试还可能放大循环 |

例如，UI 可以调用后端取消接口；SDK 也可以提供安全的截流原语。这样做不是“不可能”，而是它们若要达到本设计的前缀、工具和恢复语义，就仍然需要一个理解 DSH 调用生命周期的协调边界。

## 3. 为什么选适配器之后、已接纳流之前

这一位置同时具备四个条件：

1. **知道实际调用能力。** 可以对当前 prepared call 检查可编辑重放，而不是先删内容再赌后续可重放。
2. **看得到结构化事件。** 能区分 reasoning、普通文本、工具块和 finish；不必把工具参数中的重复字符串误当成推理来改。
3. **尚未进入下游统一接纳路径。** 暂存和拒绝尾巴仍然有意义，不用事后从多个历史/展示副本中回滚。
4. **调用循环还保有执行权。** 能取消本次调用、等待清理、决定如何结算，并在允许时发起下一次请求。

检测应该读取适配器提供的原始 reasoning，而下游只接收已经接纳的内容。由此可以把“检测依据”与“提交结果”分开：精确过滤删掉多少字符，不应成为另一个检测器是否能发现可见循环的唯一依据。

这个边界只能减少**后续**累积：已经放行的早期重复不会凭空消失，供应商未暴露的内部状态也不在可观察范围内。

## 4. 为什么是“插件做策略，Core 做执行”

### 策略插件应拥有的内容

- 有界观察窗口、重复证据、缓冲与恢复状态。
- 参数和部署取舍，如确认次数、最大保留窗口、恢复预算。
- 哪类失败允许请求一次续跑，以及说明原因的提示内容。
- 自身实例的卸载状态和计数，避免卸载后继续授权新调用。

### Core 必须掌握的内容

- 实际正在运行的异步迭代器和本次调用的取消信号。
- 当前 Agent、turn、step 和父级取消的优先级。
- 哪些 token/block 已经接纳，哪些工具尚未派发。
- 何时清理完成、持久结算是否成功、能否继续下一次请求。
- 错误是否会意外进入普通 retry 路径。

策略返回“申请中断”不等于插件可以自行拼一个新 Agent、发送伪造工具结果或绕过用户取消重试。Core 也不应该把阈值和每种重复启发式全部写死。

参考实现只允许一个输出策略拥有一次模型调用。两个编辑器同时重排同一条流，会很难说明谁持有原文、谁已经释放、谁有权取消、最终 block 应当以谁的内容为准。拒绝冲突比静默串联两个未定义的编辑策略更容易维持边界。

这里的分层不是“零 Core 成本”：调用循环、输出控制项和呈现桥接都需要配套契约。算法能放在插件里，不代表执行闭环可以由插件之外的系统自动补齐。

## 5. 实现难度主要不在“算重复率”

### 5.1 同一份原文跨越不同缓冲和最终块

流式 delta 与最终 reasoning block 可能都含有内容。如果前者过滤了，后者仍把供应商原块放入最终 message，副本会在结算时复活。

因此 [AssistantStreamAttempt.accept](../reference/packages/core/agent-loop/src/assistant-stream.ts#L59-L106) 对受控 reasoning 关闭使用已经接纳的组装结果。实时显示、compact stream 和最终消息的来源必须协调，不能靠最后再跑一次字符串替换。

### 5.2 `abort`、停止输出和完成清理是不同时间点

异步迭代器退出可能等待传输的清理。若只在清理后的 catch 分支显示通知，用户会长时间看不到确认结果；若一调用 abort 就宣称已经恢复，又可能在旧请求还没清理时误导用户。

参考实现先发布真实的本地中断事实，再请求取消；清理和结算完成以后才记录恢复提示并继续。用户/父级取消、清理异常和结算失败必须走不同路径，不能都归并成“再试一次”。

这也说明调用级 stop 不是整个任务的事务回滚，更不保证供应商立即停止计算或计费。

### 5.3 工具输出不是普通文本

部分工具 JSON 尚不可执行；完整工具块出现后又涉及正常结算的保护。如果一看到重复就取消，可能把已经完成的工具协议与调用状态拆散；若无限保护，又可能让工具块之后的输出无限延长。

所以需要“重复检测不再随意取消”与“独立结算预算”两种边界，而不是一个字符串阈值处理所有场景。工具派发与副作用的正确性依然属于原有执行链，不由检测器冒领。

### 5.4 有限恢复必须和普通 retry 分开

把 `REASONING_LOOP` 丢给通用错误重试，可能反复使用同一个被污染的上下文，甚至绕开原本的恢复次数限制。

恢复必须记录来源、保留前缀、使用明确提示，并受同一 Agent/turn/策略实例的预算约束；用户取消不得被当作可恢复循环。原生子代理也需要自己的边界，不能通过反复销毁重建子代理来伪造“次数重置后的有限”。

这里的预算仍是内存状态，不是跨进程永久配额；插件生命周期变化的影响需要诚实说明。

### 5.5 真正的实时可见性需要贯穿传输和投影

给组件增加一段中文文案不够。阶段需要从策略进入帧，再进入 Host 活动状态、重连快照、Client 折叠和 Chat 投影；旧 attempt 的迟到帧不能污染新请求。

同一个 step 内多次调用还会触发“后一个 thinking 覆盖前一个”的问题。必须区分保留前缀、当前流、正在截断和持久恢复提示。否则落盘是对的，实时界面却仍像静默停止，切换会话才暴露过程。

参见 [Host 活动基线](../reference/packages/api/session-controller/src/assistant-stream.ts#L39-L109) 和 [Chat 投影](../reference/packages/client/ui-chat/src/client/conversation-nodes/assistant.ts)。临时阶段不进模型上下文，真正恢复提示则有意进入；两者不能为了方便显示混成一种“系统文本”。

### 5.6 窗口有界不代表性能和误报问题自动消失

合法分析、代码脚手架、短填充词和编号变化会产生重复。句子切分依赖标点习惯；单个巨大 delta 与许多小 delta 又不能得到不同结果。

这要求正反例、逐字符硬上限、真实迁移顺序和性能快路径共同验证。算法本体看似较小，工程却还包括协议一致性、类型消费者、生命周期、历史兼容与测试维护。

## 6. 现实中的取舍

- **不保证完全避免 CoT 污染。** 等待证据与及时放行正常推理之间存在不可消除的取舍；已经提交的内容不做追溯语义清洗。
- **不把所有模型拉到同一编辑能力。** 签名/不透明路由可以继续使用模型，但不能靠丢元数据换取编辑能力。
- **不把停止误当任务成功。** 恢复后真实工具调用是有意义的进展；有限恢复后明确失败，也可能比继续无限消耗更便于交接。
- **不保证每个状态都能肉眼逐个看到。** 一个大 delta 可以在很短时间内包含多个迁移；UI 应最终呈现真实当前状态，而不是为了演示延迟处理。
- **不保证上下文总能救回。** 已经严重累积冗余的会话仍可能需要人工摘要或重新整理；当前守卫没有自动交接、模型选择或会话迁移功能。
- **不保证固定 token 节省比例。** 计费、远端生成和取消响应依赖适配器与供应商，不能仅凭本地中断码推导节省额度。

因此这层做的是一个可解释的**止损与继续决策边界**：尽量在仍有机会行动或交接时停下来，而不是等整个会话和剩余预算都变成循环历史后再补救。

## 7. 可以讨论的其他架构

具备完整调用语义的 SDK、中间层或统一模型网关，也可能实现同类机制；如果未来上游提供更完善的输出治理扩展点，策略插件也可以更薄。重点不是文件必须放在哪个目录，而是下列责任有没有明确拥有者：

1. 原文和已接纳内容的唯一真值。
2. 编辑能力的可信来源。
3. 本次调用、父级取消和清理顺序。
4. 持久结算、工具派发与恢复预算。
5. 实时状态、重连与历史事实的一致性。

如果其他方案能完整承担这些责任，就不是概念上不成立；如果只提供一个重复正则或一个 toast，则尚未解决这里描述的整体问题。
