# 设计思路与工作原理

[返回首页](../README.md) | [English](DESIGN.en.md)

## 1. 问题不是“文字重复”这么简单

模型可能不断输出“我应该读取文件”“现在执行”“不要再循环”，却迟迟不发出真正的工具调用。字句会交替、插入语气词、改变编号，因此整段字符串没有完全相同的副本，精确去重可能始终没有足够证据。

另一端也有风险：正常分析会多次出现相同术语、代码脚手架和口头填充词。若直接按重复字符占比删除内容，会把新的变量名、计数和否定判断一并抹掉。

因此本设计拆开两种不同权限：

1. **删除副本**必须有精确原文证据。
2. **判断正在停滞并停止调用**可以使用保守的组合启发式，但只能丢弃尚未提交的尾巴，不能把模糊相似的句子剪贴成一段新历史。

这不是语义推理正确性分类器。它只治理实际可见的流式输出。

## 2. 目标、非目标与不变量

### 目标

- 在显示和持久提交之前治理新增输出，实时显示与后续重放使用同一份已接纳内容。
- 正常输出不先扣住一个完整缓冲区；有证据后才开始扣留。
- 暂存、证据窗口、取消和续跑都有边界。
- 截断只影响本次模型调用，用户仍可明确取消整个任务。
- 检测过程立即可见，不需要切换会话才看到流程。

### 非目标

- 不修改模型内部隐藏状态，不检测没有输出的“内部思考”。
- 不保证识别所有语义循环，不保证零误报。
- 不对答案内容或代码正确性作保证。
- 不为签名推理提供删签名兼容回退。
- 不把本参考仓库做成通用安装包。

### 必须保持的不变量

- 已经放行的字符不被可见停滞检测器回滚、重排或改写。
- 未经证实的暂存文本，恢复时按原顺序释放。
- 只有精确副本检测器可以抑制已证实的副本。
- 检测器不派发工具，不执行部分 JSON 参数。
- 取消优先于恢复；清理失败不能开启下一次调用。
- 实时状态不是模型 token，也不是伪造的人类输入。

## 3. 职责分层和数据路径

```text
prepared model call（能力已确定）
  -> reasoning 输出策略
     -> VisibleStallWatch：原始字符上的停滞证据与暂存
     -> ReasoningWatch：精确副本证据与过滤
  -> AssistantStreamAttempt
     -> 已接纳 token/chunk：组装、持久流、实时输出
     -> 检测 stage：仅实时帧与活动调用快照
  -> 当前调用取消 / 安全前缀结算
  -> 有来源标记的续跑提示
  -> 同一活动内下一次模型调用
```

关键文件可在[参考源码索引](../reference/README.md)找到。它们保持原项目路径，便于对照调用链，但并非独立编译工程。

可见停滞检测必须先看到原始字符，而不能只观察“被精确过滤后还剩什么”。否则检测器会依赖另一个检测器的删除量；短句微变循环恰好可能没有任何可删除副本。

策略以字符为单位推进内部观察位置，供应商把文本切成一个巨大 delta 或很多小 delta，不应改变判定结果。同一 delta 内的多次阶段迁移按发生顺序保留。

## 4. 精确副本检测：什么时候才有权删除

参考实现：[reasoning-watch.ts](../reference/packages/guard/repeat-tool-reminder/src/reasoning-watch.ts)。

### 4.1 有界证据

检测器分别保留原始后缀、已接纳后缀以及待定片段。默认原始/已接纳窗口各 4096 个 UTF-16 码元，内部每 32 码元观察一次。暂存片段记录原始偏移，方便把被证明属于副本的区间映射回待定内容。

`normal -> tentative -> suppressing` 是这一路自己的状态机：正常内容立即输出；重复证据达到 hold 门槛后，之后的内容才变成待定；达到 confirm 门槛后才允许删除副本区间。

### 4.2 两类精确证据

- **周期尾缀**：搜索长度至少 4、最多默认 192 的周期，要求至少三个周期相符；空白或单一字符等无信息模式被排除。
- **重排句子池**：完整句子单元的原文重复，即便次序不同也能形成证据。默认至少 16 个单元，重复单元字符占比至少 0.75。

候选副本还需要在已接纳后缀中找到对应原文。抑制区间排序合并后，只从待定片段中删除，不回写已经输出的前缀。数字、标识符、否定词变化不会被归一化成相同句子。

### 4.3 取消与恢复

默认累计抑制 16384 个码元、且当前仍有重复证据时，才触发这一路的取消。这个门槛不是可见停滞检测的“最大缓冲区”，两者不同。

`flush()` 释放未证实片段；已抑制的精确副本不会重新出现。屏障结算使用 `release()`：继续过滤已经证实的副本，但禁止在一个已经来不及取消的结算动作中产生新取消，从而避免丢掉应当交付的字符。

## 5. 可见停滞检测：水坝如何工作

参考实现：[visible-stall.ts](../reference/packages/guard/repeat-tool-reminder/src/visible-stall.ts)。

### 5.1 参数与单位

所有字符预算都是 **UTF-16 码元**，不是 token、UTF-8 字节、字形数或秒数。

| 字段 | 默认 | 作用 |
|---|---:|---|
| `windowChars` | 1024 | 初始观察窗 |
| `maxWindowChars` | 8192 | 当前实现允许的硬上限，配置不得超过它 |
| `scanChars` | 128 | 观察节奏 |
| `minUnits` | 16 | 至少这么多完整句子单元 |
| `unitShare` | 0.5 | 重复单元的出现次数占比 |
| `unitCharShare` | 0.15 | 重复单元承载的字符占比 |
| `shingleChars` | 8 | 精确片段长度 |
| `shingleShare` | 0.6 | 重复片段覆盖比例 |
| `confirmWindows` | 3 | 连续命中次数 |
| `recoveryWindows` | 2 | 连续未命中次数 |

配置错误在策略启用时明确报错，不静默夹紧成另一套参数。

### 5.2 第一道证据：句子确实在复现

句子单元由以下终止符划分：`。！？!?；;`、回车和换行。ASCII 句点 `.` 不是终止符。单元边缘会 trim 空白；不会把单元内部的数字、变量名或否定语句归一化。

设窗口中完整非空单元为 `u1 ... un`，`count(u)` 为该单元原文的出现次数：

```text
R_units = sum(count(u), for count(u) > 1) / n
R_chars = sum(count(u) * length(u), for count(u) > 1)
          / sum(length(ui), for all occurrences)
```

必须同时满足 `n >= 16`、`R_units >= 0.5`、`R_chars >= 0.15`。

`R_chars` 用来防止“好。”之类很短的复现口头语驱动整个判定：即便它出现次数很多，窗口中若主要是持续更新的分析句子，也不应仅因此拦截。

### 5.3 第二道证据：字符片段也在被复用

对原始窗口扫描长度为 8 的精确 shingle。相同片段至少相距 `2 * shingleChars`，才作为复现证据，避免把附近重叠本身当作重复。

实现用哈希桶找候选，但哈希相同后仍逐码元比较，不把哈希碰撞当成相等。覆盖数组统计符合条件的后出现片段所覆盖的位置，每个位置最多计一次：

```text
R_shingle = covered_positions / raw_window_length
qualifies = enough_units
            AND R_units >= 0.5
            AND R_chars >= 0.15
            AND R_shingle >= 0.6
```

这不是编辑距离、向量相似度或语义模型。片段重用本身不够，句子复现本身也不够，必须联合成立。

### 5.4 从正常到暂存

- 未收满初始观察窗时，正常放行。
- 完整观察窗首次命中时，将 `holding` 置为真，`high = 1`。
- **触发这次观察的当前字符仍然放行**；从后续字符开始暂存。
- 暂存中的原文是 `raw` 的后缀，仅记录后缀长度，不另外复制一份完整的 pending 字符串。

因此“1024 的观察窗”不意味着每个请求都先延迟 1024 字符。

### 5.5 扩窗、连续确认与恢复

暂存期间，观察容量在满足扩容条件时翻倍，最大 8192；正常观察初始只用 1024。扩窗后不一定每次拥有完整容量，判定仍要求至少初始窗口那么多原始字符。

- 命中：`high += 1, low = 0`。
- 未命中：`high = 0, low += 1`。
- 未受工具保护，连续命中达到 3：丢弃未提交的暂存尾巴，结束本次调用。
- 连续未命中达到 2：按原顺序释放暂存内容，并重置观察。

“连续 3 次”是**观察次数**，不是 3 个供应商 chunk，也不是一定要收满 3 个互不重叠窗口。初次命中已算第一次，后两次可以提前确认，不必等到 8192。

水坝释放的内容随后还会经过精确副本检测器。因此“水坝原样释放”不等于“整个组合策略绝不再过滤其中已证实的精确副本”。

### 5.6 上限处不是无条件泄洪

每个字符处理都保证保留窗口不超过 `maxWindowChars`。暂存后缀达到上限时，立即用当前证据决定：

- 未受工具保护且证据仍命中：截断并丢弃未提交尾巴。
- 证据已回落，或已受工具保护：释放并重置。

即使确认次数被设得很大，也不能靠“到顶就放行”让明显循环无限周期性通过。

8192 只约束这一个检测器的原文窗口。精确副本窗口、哈希桶、覆盖数组、应用历史和模型 token 另有占用，不能宣称整个系统只用 8192 字节或常量时间。

## 6. 围栏、屏障与真实原因

可见停滞检测用不保存整行文本的状态机识别 fenced code：

- 行首最多 3 个空格；至少 3 个同类反引号或波浪号。
- opener 可以带 info string；反引号 opener 的信息部分不能再含反引号。
- closer 必须同字符、长度不短于 opener，后面只允许空白。
- 行内反引号、4 空格缩进、4 反引号内的 3 反引号不当作有效闭合。
- 在完整围栏行的换行边界确认开闭；围栏内暂停可见停滞观察，开闭时释放未决尾巴并重置窗口。

`released` 在通常恢复路径表示证据回落；`barrier` 表示围栏或显式结算迫使释放，**没有对重复率作判断**。两者不能混为同一句严格的原因证明。当前参考实现有一个粒度限制：受工具保护后，连续命中或达到上限也可能主动释放，并共用 `released`。因此 UI 的“重复率回落”不能被当作所有放行情形的真实原因；本仓库如实记录该限制，不修改参考源码。

普通非推理事件到来前也需要结算待定推理，保持事件顺序。围栏仅暂停可见停滞检测，并不意味着精确副本检测器自动获得代码语义知识；代码大量精确重复仍是需要评估的边界。

## 7. 能力门：谁有权编辑输出

参考实现：[plain-reasoning.ts](../reference/packages/llm/llm-pi-ai/src/plain-reasoning.ts)。

策略必须由配置显式启用，且**同一次 prepared call** 必须声明 `reasoningReplay: 'editable-plain'`。只有插件开关、供应商名称或模型显示名都不够。

pi-ai 适配器的显式 plain 模式只对应检查过的 Chat Completions 转换路径。已知纯文本字段选择器 `reasoning_content`、`reasoning`、`reasoning_text` 与加密/签名元数据不是一回事。出现 redacted thinking、不认识的 thinking signature、text/tool signature 时，必须明确拒绝不兼容重放，不能先删除元数据再假称可编辑。

未知和不透明路由保持原样；不是说这些模型不能使用 DSH，而是它们不走本输出编辑路径。其他适配器是否能支持，必须重新审查其真实协议与重放契约。

推理-only 安全前缀的重放也需要适配器配合：若同一路径会把只有 reasoning、没有 text/tools 的消息丢掉，则需要保留原文的安全转换；这不是允许跨供应商抹掉签名。

## 8. 调用级取消、结算与有限续跑

参考实现：[agent.ts](../reference/packages/core/agent-loop/src/agent.ts) 和 [reasoning-policy.ts](../reference/packages/guard/repeat-tool-reminder/src/reasoning-policy.ts)。

### 8.1 先通知，后等待清理

```text
策略确认中断
  -> 发布真实 failure code=REASONING_LOOP 的 finish 帧
  -> abort 当前调用的 AbortController
  -> 退出迭代并等待 iterator.return / 传输清理
  -> 成功清理后写入 interrupted assistant 前缀
  -> 写入有来源的续跑提示
  -> 如预算允许，开始下一次调用
```

finish 帧在清理前发布，避免清理慢时 UI 完全静默。这个 finish 是策略确定的真实本地失败，不伪装成正常 stop 或 token 上限。清理完成前只能显示“正在截断”，不能宣称下一次请求已经开始。

### 8.2 安全前缀和整块回灌

只提交已接纳的 reasoning/text 安全前缀。未派发的工具不作为成功工具调用写入前缀。最终 reasoning block 必须由已接纳文本关闭，不能把供应商携带的原始整块重新灌回来，否则已经去掉的副本会复活。

无可交付前缀时可结算为 `assistant/attempt`；正常有前缀时结算为 `assistant/message` 且 `interrupted: true`。

### 8.3 续跑不是无限重试

恢复计数保存在按 Agent 隔离的 WeakMap 中，按 turn 更新。默认 `maxRecoveries = 1`；配置为 3 时，最多追加 3 次调用，不含最初调用。`0` 表示不续跑。

达到恢复预算后返回真实失败；不能进入普通 `always` 请求重试分支绕开预算。原生子代理在自己的 Agent/turn 内使用同样的有界机制，不把整个父任务取消再重建子代理。

计数是策略实例的内存状态，不是跨进程永久配额。插件重载或进程重启不应被描述为沿用同一份全局恢复预算。

### 8.4 提示词确实进入模型上下文

状态通知不进入模型上下文，但**恢复提示本身有意进入**。它是带专属来源的持久 `user/message`，不是人类用户发出的指令：

```json
{
  "kind": "reasoning-loop-recovery",
  "turn": 1,
  "step": 1,
  "attempt": 1,
  "limit": 3
}
```

这是结构示意，不是某个真实会话。可见停滞分支的提示明确说“未证实的重复尾巴被丢弃”；精确副本分支才说“重复副本已删除”，不能混淆依据。提示要求换一种方式完成尚未完成的任务，并使用真正的工具协议。

用户/父级取消、插件卸载、迭代器清理失败或持久结算失败，都会阻止策略授权的下一次请求。已捕获的策略可能继续完成当前调用的过滤/停止，但卸载不能继续授权恢复。

## 9. 工具安全与结算预算

完整工具块在协议上完成后，检测器执行 `protectCommit()`。此后可以继续暂存/释放，但不再因重复证据随意取消该调用。**保护不是派发工具，也不是允许执行部分参数。**

为了防止“已经给了工具块，但之后无限继续输出”绕开边界，首次完整工具块后启用独立 `settlementBudget = 65536`：每个后续非 finish 事件耗费 `1 + 新 delta 的 UTF-16 长度`，另一个工具块不会重置它。

超限时返回 `TOOL_SETTLEMENT_LIMIT`，不派发这次调用中的工具，也不自动续跑。它不是 `REASONING_LOOP`，UI 不应伪称已经识别出重复推理。

这是输出量预算，不是时间超时。供应商无输出时，仍依赖适配器自己的 idle watchdog。

## 10. 实时链路与持久链路为何分开

参考实现：[AssistantStreamAttempt](../reference/packages/core/agent-loop/src/assistant-stream.ts)、[Host 折叠器](../reference/packages/api/session-controller/src/assistant-stream.ts)、[Client 折叠器](../reference/packages/api/session-controller/src/client/sessions/assistant-stream.ts)。

### 10.1 实时阶段

策略产生 `reasoning-stall` 控制项，携带 `suspected / released / barrier`。它变成带 `attemptId / revision / turn / step / index` 的 `stage` 帧，**不进入**文本 accumulator、模型请求或持久 token 流。

Host 仅更新当前匹配 attempt 的状态，活动快照保留最近一个 stage。Client 将它折叠为临时展示事件。在此参考实现中，为兼容既有投影，`assistant/live-chunk` 的载荷是 `chunk | stage` 联合；消费者必须判别，不能把 stage 当文本。

因此“只新增 UI 文案”不够，生产者、传输、重连快照、消费者、投影都要同步。headless/token 消费者应忽略这种纯展示帧。

### 10.2 持久事实

截断结算和恢复提示按顺序持久记录。真正已经结束的探测阶段不会在打开历史时伪造重放。

| 场景 | 应看到什么 |
|---|---|
| 当前连接、正在缓冲 | 当前疑似状态 |
| 断线重连、调用仍活跃 | 活动快照恢复的最近阶段 |
| 打开已结束历史 | 截断前缀、恢复提示等持久事实；没有探测阶段流水账 |

未匹配的旧 attempt、结算后迟到帧、取消后的 release，不应制造幽灵状态。

## 11. 同一步内多次调用的 UI 问题

如果一个 step 只保存最新 assistant block，恢复调用会覆盖旧 thinking。若所有 `interrupted` 都呈现成“已停止”，用户又无法区分手动停止与守卫本地截断。恢复提示若被当作隐藏 context，即使落盘也不可见。

参考实现对这些问题分别处理：

- `retained` 保留被后续调用取代的截断前缀；新输出不覆盖历史前缀。
- `interruption` 表示本次真实策略 finish，优先于旧 `recovery`；第二次截断时不能仍显示第一次正在恢复。
- `recovery` 使用持久来源里的 turn/step/attempt/limit 定位和计数，提示词可以展开查看。
- `stall` 只表示实时水坝阶段，同一行随状态迁移更新，不逐字符提醒。
- 结算或 step 关闭时清理过期阶段；普通用户取消仍显示用户停止，而不是自动恢复。
- 锚点优先使用保留前缀的持久序号，减少实时分数序与历史整数序造成的位置漂移。

参见 [Chat 投影](../reference/packages/client/ui-chat/src/client/conversation-nodes/assistant.ts) 和 [RecoveryNotice](../reference/packages/client/ui-chat/src/client/chat/RecoveryNotice.tsx)。同一个长期保留状态行不代表把每次探测都写进日志。该实现还可能在截断结算与下一条恢复事件之间短暂保留上次恢复的呈现；它不是新的模型请求已经开始的证据。

## 12. 性能取舍和边界

后续维护提取了[句子扫描辅助函数](../reference/packages/guard/repeat-tool-reminder/src/sentence-units.ts)：

- 先数终止符；不足最少单元数时，不运行可能在长无终止符字符串上开销较大的句子正则。
- 周期信息检查避免为每个候选周期反复分配 slice/Set。
- 哈希碰撞仍做原文比较，不用性能换正确性。

窗口有界不等于 CPU 零成本，更不能声称整体固定时间。高重复率、合法重复、文本语言和标点习惯、很短循环、无句子终止符、多个 reasoning block，都影响灵敏度。

策略只主动过滤首个选中的 reasoning index，其他 index 和非 reasoning 内容按其结算边界处理。它不是对最终答案 text 的通用去重器。

围栏识别发生在完整行的换行边界；在行尚未收完时，不能靠未来信息预知它是不是围栏。巨量单个 delta 内也可能包含多个迁移，UI 实际收到时可能很快收敛到最新状态，不保证用户肉眼逐个看到每个中间状态。

## 13. 如何理解验证结果

[验证记录](VALIDATION.md)区分三层：检测器性质、调用/投影组合测试、真实模型/真实 UI 行为。当前发布前在原源码工作区有 275 项相关测试通过；这不等于证明所有语言、所有路由或任意用户部署都正确。

一个重复片段本来会在更后面自行恢复，也可能提前触发本守卫。这是主动止损与误拦之间的产品取舍，不应把阈值包装成准确率保证。
